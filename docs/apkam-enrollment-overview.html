APKAM enrollment — how it works

APKAM (Application PKAM) is how an atSign owner lets an individual app or device act on their behalf — with just the access it needs, revocable at any time, and without ever handing over the root keypair. This is a conceptual overview: it starts with the idea and what it enables, then serves as an engineering reference for the flows, the per-enrollment namespaces, and the authorization model.

Overview · a level above the code

1The idea, and what it enables

Onboarding an atSign creates one root keypair that authenticates the owner and can do anything. Giving that key to every app and device would be all-or-nothing and irreversible. APKAM enrollment replaces that with a set of scoped, revocable grants: each app or device gets its own key and only the namespaces it needs, and can be turned off later without disturbing anything else.

The unit is an enrollment — one (app, device) with its own signing keypair, a namespace-scoped grant, a lifecycle you approve and can later revoke, and a one-time delivery of the encryption keys it needs to work with the atSign's end-to-end-encrypted data. What that model buys you:

  • Least privilege. An app holds only the namespaces it needs, at read or read-write — never the root key. A photo app gets photos:rw, not the keys to everything.
  • Revocability without re-keying. A lost device is revoked in place; the owner and every other app keep working. No root-key rotation, no re-onboarding.
  • Safe key delivery. Each enrollment still needs the atSign's encryption keys to read and write E2E-encrypted data. They are delivered to it encrypted, once, at approval — the server never sees anything in the clear, and the private signing key is never transmitted.
  • Delegated administration. A trusted enrollment can be given the right to manage others — bounded so it can never grant access it does not itself hold.
  • Isolation & auditability. Every enrollment is a durable record, and each one's private working data is walled off from the others.

2The building blocks

An enrollment record

  • app / device name — what and where.
  • namespaces — a map of namespace → r | rw; * means all namespaces; __manage means management rights.
  • APKAM public key — verifies this enrollment's logins. The private half lives only on the device.
  • state — pending, approved, revoked, denied (see §6).
  • delivered key material — the atSign's encryption keys, encrypted for this enrollment (§5).
  • metadata — opaque data the enrollment chooses to publish to other authorized enrollments.

Two special namespaces

  • __manage — the management namespace. Holding it (read-write) confers the authority to run enrollment operations, and it is where enrollment records and delivered key material physically live.
  • <id>.a|r|d.__e — each enrollment's own per-enrollment reserved namespace (§4): a private space keyed to the enrollment, with an approved / revoked / deleted marker.

The owner — a root-authenticated connection with no enrollment id — sits above all of this and bootstraps the first enrollment.

3Enrollment-management flows

3.1 Bootstrap — the first enrollment

  1. The owner authenticates with the root credential and requests enrollment of the first app.
  2. Because it is the owner, the request is auto-approved and granted *:rw plus __manage — a full-access administrator enrollment that can then manage everyone else.

3.2 New enrollment — an app joins

  1. A manager (the owner, or any enrollment holding __manage) issues a short-lived one-time passcode (OTP) — or a longer-lived semi-permanent passcode.
  2. The new app sends an enrollment request carrying that passcode, the namespaces it wants, its APKAM public key, and its symmetric key (encrypted). It is recorded as pending. Requests are rate-limited, and the passcode is consumed.
  3. A manager approves — supplying the atSign's encryption keys re-encrypted for the new enrollment (§5). Approval can only grant namespaces the manager itself holds.
  4. The app APKAM-authenticates (proving possession of its private key), pulls its delivered keys once, and stores them on-device. It is now a live, scoped enrollment.

3.3 Lifecycle changes

  • Deny — reject a pending request.
  • Revoke — withdraw an approved enrollment's access (e.g. a lost device). Its live connection is dropped and its per-enrollment data moves from the approved to the revoked marker.
  • Unrevoke — restore a revoked enrollment.
  • Delete — remove a denied or revoked record entirely; its per-enrollment data moves to the deleted marker. Expiry (an enrollment can be given a lifetime) reaches the same end state.

All four are management operations: they require __manage and are further bounded so the caller can only act on an enrollment whose namespaces the caller itself holds — you cannot revoke or approve an app for a namespace you don't have. You cannot revoke your own enrollment without an explicit force flag.

3.4 Inspection & discovery

  • List — without __manage a caller sees only its own record; with __manage it sees the full roster.
  • List-by-namespace — any approved enrollment holding at least read on a namespace can discover the other enrollments that also have access to it (id, access level, public key, published metadata). A deliberate discovery mechanism — it never returns any secret.
  • Fetch by id — retrieve one enrollment's details, including its delivered key material. Permitted for your own enrollment, or for another only if you hold __manage and access to every namespace that enrollment holds.

4Per-enrollment namespaces — <id>.a|r|d.__e

Every enrollment is automatically given read-write on a reserved namespace unique to it. The trailing marker tracks the enrollment's lifecycle — .a.__e while approved, moved to .r.__e when revoked and .d.__e when deleted — so an enrollment's working data follows its state automatically and is cleaned up with it.

What it enables

  • Private per-enrollment storage. A place an enrollment keeps its own working data, isolated from every other enrollment.
  • Discovery target. An enrollment can publish a public key here (for example its signing key) so other authorized parties can find it and encrypt to it — this is what list-by-namespace surfaces.
  • Automatic lifecycle hygiene. Revoke, delete and expiry move or remove this data as a side effect, so there are no orphans.

Isolation. This namespace is private to its owning enrollment: another enrollment cannot read or write it. Public keys stored there remain world-readable, but private data does not cross between enrollments.

5Key material & delivery

Because atSign data is end-to-end encrypted and the server never holds decryption keys, a new enrollment must be given the atSign's encryption keys — safely. Four pieces of material are involved:

MaterialWhat it isHandling
APKAM keypairThe enrollment's own login keypair.Public half on the record; private half never leaves the device.
Encrypted symmetric keyThe enrollment's symmetric key, encrypted to the atSign's encryption public key.Supplied at request time; used to wrap the keys below.
PEKThe atSign's default encryption private key, re-encrypted for this enrollment.Supplied at approval, stored server-side under __manage, pulled once by the enrollee and kept on-device; the server copies are unused thereafter.
SEKThe atSign's default self-encryption key, re-encrypted for this enrollment.

Delivery is one-shot and encrypted end to end. The manager approving the request does the re-encryption; the server only stores and relays ciphertext. The enrollee reads its PEK/SEK once, through a dedicated key-retrieval path scoped to its own keys, and holds them locally from then on.

Each mutation enforces a state precondition — you can only approve a pending enrollment, revoke an approved one, unrevoke a revoked one, and delete a denied or revoked one.

7Authorization model — summary

Two questions govern almost everything: do you hold __manage? (the right to administer enrollments) and do you hold the namespace in question, at a sufficient access level? The owner connection sits above both. Management authority is always bounded by your own grants — holding __manage is necessary but never sufficient to act on namespaces you don't have.
